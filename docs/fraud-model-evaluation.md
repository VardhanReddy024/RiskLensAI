# Fraud Model Evaluation

RiskLensAI classifies potentially fraudulent Razorpay payments with a deterministic binary logistic-regression model. The model is intentionally small and dependency-free so its training and evaluation are reproducible from the repository.

## Dataset

The dataset is synthetic and generated deterministically in `src/data/fraud_dataset.ts` from a fixed mathematical seed. It contains 500 labeled transaction feature rows. It is not a production merchant or Razorpay dataset, so these metrics are development evidence only.

The split is deterministic and shuffled by the seeded generator:

- Training rows: 429
- Held-out test rows: 71
- Test labels are never used by model training or prediction.

Run the evaluation with:

```text
npm run model:evaluate
```

## Features

The classifier uses eight numeric features derived from the existing transaction schema:

- Amount ratio against the currency baseline
- Distance score
- Device risk
- New-device indicator
- Network reputation risk
- Merchant-category risk
- Authentication risk when 3DS is absent
- Irreversible payment-rail indicator

## Model and Decisions

The model is binary logistic regression trained with deterministic batch gradient descent. It emits a fraud probability and a compatible 1-99 risk score.

Thresholds are configured in `src/data/fraud_dataset.ts`:

- `ALLOW`: probability below `0.30`
- `REVIEW`: probability from `0.30` up to `0.75`
- `BLOCK`: probability at or above `0.75`

The existing Razorpay API contract maps `BLOCK` to `REJECT` for persisted `riskDecision` values.

## Measured Held-Out Results

These values are generated by `npm run model:evaluate`; they are not hard-coded:

- Precision: `1.0000`
- Recall: `0.9333`
- F1: `0.9655`
- False-positive rate: `0.0000`
- Confusion matrix: TP `28`, TN `41`, FP `0`, FN `2`

The model's reported ROC-AUC is computed from pairwise ranking on the held-out set and is exposed in each prediction's model metadata.

## False-Positive Cost

The configured development assumption is `USD 25` per legitimate transaction incorrectly classified as fraud at the evaluation threshold. This is an explicit operational assumption, not a measured loss estimate. The reported false-positive cost is:

`false-positive count * configured false-positive cost`

Real merchant loss estimates require labeled Razorpay outcomes such as chargebacks, refunds, and confirmed fraud investigations.
